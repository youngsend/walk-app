# walk-app テストケース

最終更新: 2026-08-08

要件は [requirements.md](./requirements.md)、設計は [design.md](./design.md)、作業手順は [development-plan.md](./development-plan.md) を参照。

## 方針

**テスト駆動で進める。** 実装より先にテストを書き、落ちることを確かめてから実装する。

| 項目 | 内容 |
|---|---|
| 実行 | `npm test`（監視は `npm run test:watch`） |
| 構成 | `jest-expo` プリセット |
| 置き場所 | `__tests__/<モジュール名>-test.ts` |

この表の「ケース」は、テストコード中の `it(...)` の文言とそのまま対応させる。
片方だけ変えないこと。

**照合はテストで自動化してある**（`__tests__/test-cases-doc-test.ts`）。
md に載っていない `it(...)` があるとテストが落ちる。

| ケース | 目的 |
|---|---|
| すべてのテストケースが md に載っている | 記載漏れを機械的に捕まえる |
| テストケースを 1 件以上見つけられている | 正規表現が壊れて 0 件になり、素通りするのを防ぐ |

## 何をテストで押さえ、何を実機で見るか

`lib/` は純粋なロジックなので、実機なしで確かめられる。
実機が要るのは、地図の描画・GPS・実際に歩いた結果だけ。

| 対象 | 確認方法 |
|---|---|
| タイル計算、コストモデル、グラフ構築、経路探索、投入の判断 | **自動テスト** |
| PBF からの抽出結果 | Mac。生成時に出る値を[実測値](#実測値との突き合わせ)と突き合わせる |
| 地図表示、現在地、ルート描画、DB の転送 | 実機（室内） |
| 幹線回避が体感に合うか、多様性、バッテリー | 実機（外を歩く）。[動作確認の場所](./development-plan.md#動作確認の場所) |

## lib/tiles.ts — タイル計算

`__tests__/tiles-test.ts`

### tileAt

| ケース | 目的 |
|---|---|
| 開発エリアが実測したタイルと一致する | 実測に使った bbox とズレていないことの固定 |
| タイル境界ちょうどの座標が、そのタイルの内側に入る | **回帰テスト。** 度のまま割ると `139.70 / 0.02 = 6984.999999999999` となり、境界の座標が隣のタイルに落ちる |
| 任意の座標が、自分のタイルの範囲内に収まる | 2 万点の走査。境界の取りこぼしが無いこと |
| 小数 7 桁より細かい差は無視して上のタイルに入れる | OSM の座標精度に丸める仕様の明示 |
| 負の座標でも下側に丸める | 赤道・本初子午線をまたぐ側の挙動 |

### tileBounds

| ケース | 目的 |
|---|---|
| 誤差のない値を返す | 浮動小数の誤差が境界判定に漏れないこと |
| 1 辺が TILE_SIZE になる | [タイルの定義](./design.md#21-タイルの定義)どおりの大きさ |
| 隣接タイルが隙間なく接する | 取りこぼし・重複が出ないこと |

### tileKey

| ケース | 目的 |
|---|---|
| 往復して元に戻る | DB のキーに使うため |

### tilesAround

関東全域を入れると保存済みタイルは 8,000 枚を超える。
**読む範囲は常にここで絞る**（全部まとめて読むとメモリに載らない）。

| ケース | 目的 |
|---|---|
| 半径 0 なら中心の 1 枚だけ | |
| 半径 1 なら 3×3 の 9 枚 | [規模の見積り](./design.md#24-規模の見積り)の「3×3 タイル」に対応する単位 |
| 中心を必ず含む | 現在地のタイルが落ちないこと |
| 同じタイルを二度返さない | 重複して読まないこと |

### tilesForRoute

経路が通りうる範囲を**楕円**で切り出す。矩形だと経路が絶対に通らない隅まで読む。

**なぜ楕円で漏れないか。** 総距離が L 以下の経路上の任意の点 p は
`d(出発, p) + d(p, 目的) <= L` を満たす。この和が L を超える点を通る経路は
必ず L より長いので、焦点を 2 地点に置いた楕円が**ちょうど**探索範囲になる。

| ケース | 目的 |
|---|---|
| 同じ地点なら、その 1 枚を含む | 距離 0 でも落ちないこと |
| 出発地と目的地のタイルを必ず含む | 両端が入らないと経路が引けない |
| 直線上のタイルを取りこぼさない | 2 点を結ぶ線を 100 点に刻んで全部含まれること |
| 遠回りを許す範囲だけ横に膨らむ | 許容倍率を上げると範囲が広がる |
| 矩形より狭い | **読み込みを減らす根拠。** 外接する長方形より少ないこと |
| 同じタイルを二度返さない | |
| タイルの辺の真ん中にいても、そのタイルを返す | **回帰テスト。** 中心と四隅の 5 点でしか判定しておらず、辺の中央はどの標本点からも遠いため、**出発地を含むタイル自身が落ちて 0 枚になり**、画面に「道路網が入っていない」と出ていた |
| タイルのどこに立っても、そのタイルを返す | 1 枚を 20×20 に刻んで走査。取りこぼしが無いこと |

**フィクスチャの注意:** 起点にタイルの角を使わないこと。開発エリア
(35.62, 139.7) はちょうどタイル 6985/1781 の南西角で、そこを起点にすると
上のバグが素通りしてしまう（実際に見逃した）。

## lib/cost.ts — コストモデル

`__tests__/cost-test.ts`

| ケース | 目的 |
|---|---|
| 設計表の値を返す | [種別係数](./design.md#13-コストモデル)と実装のズレを防ぐ |
| 歩いて気持ちのいい道はどれも同じ係数になる | `pedestrian` `footway` `path` `living_street` `residential` `unclassified` `service` `steps` は**作者がどれも同じくらい好き**なので区別しない。差を付けても好みを表さず、A\* の推定値を緩めて探索を遅くするだけ |
| 好きな道より幹線が高い | **大小関係そのものが要件。** 値を調整しても壊れてはいけない順序 |
| 接続路は接続元と同じ係数になる | 実データにある `primary_link` などの扱い |
| 表に無い種別は 1.0 になる | `cycleway`・`rest_area`・`corridor` など、設計表で網羅できていない種別 |
| 接続元も未知なら 1.0 に落ちる | フォールバックの二段目 |
| タグが無ければ補正しない | `lanes` は日本の生活道路にほぼ無い（[前提調査](./design.md#11-前提調査-lanes-タグは使えない)） |
| 2 車線以上は 1.5 倍 / 1 車線以下は 0.9 倍 | 補正の値 |
| 解釈できない値では補正しない | `lanes=unknown` のような実データ |
| 複数値や小数でも先頭の数値で判断する | `lanes=2;3` のような実データ |
| 種別係数と車線補正を掛け合わせる | `primary` かつ 2 車線 → 12.0 |
| 車線タグが無ければ種別係数そのまま | 補正が勝手に掛からないこと |
| highway が無くても落ちない | タグ欠損への耐性 |

### edgeFactor — footway の種別

関東全域の実測で `highway=footway` の **6 割が歩道と横断歩道**だった
（[footway の 6 割は道路の付属物](./design.md#111-footway-の-6-割は道路の付属物)）。
車道に付随する線を好きな道と同じ扱いにすると、**大通り沿いの歩道が最も安い道になり**、
「幹線を避ける」が骨抜きになる。

| ケース | 目的 |
|---|---|
| **幹線沿いの歩道は、その幹線と同じ係数になる** | **ここが肝。** 幹線に 8.0 を付けても歩行者はその車道を通らず、並走する歩道を通る。歩道が安いままなら**減点が丸ごと迂回されて意味を失う** |
| 歩行不可の道路沿いの歩道は通行可能な上限になる | `trunk` / `motorway` 自体は歩けないので親の係数が無い。沿って歩くのは最悪なので上限 8.0 を当てる |
| 沿う幹線が分からない歩道は好きな道と同じにする | 生活道路の歩道がここに入る。別線歩道の 8% がそれだった |
| 種別が無い footway でも、幹線沿いなら幹線の係数になる | `footway` の 39.4% は `footway=` が無く、遊歩道と無記名の歩道が混在。**タグでは見分けられないが隣に幹線があるかは座標で分かる** |
| 歩行者専用の道はどれも幹線沿いなら継ぐ | `path` `pedestrian` `steps` も車道に付随して描かれる。歩道橋の橋げたもここ |
| 横断歩道は along があっても継がない | 横断は避けようがない |
| 車道そのものは along を見ない | `residential` や `tertiary` は自分の種別で決まる |
| 横断歩道は基準と同じにする | `footway=crossing` は 1.0。横断は避けようがないので、優遇だけ外す |
| 種別の無い footway は好きな道と同じ係数になる | 公園の遊歩道・参道など。歩道と決めつけない |
| 知らない footway 種別なら好きな道と同じままにする | `access_aisle` や `traffic_island` |
| footway 以外の種別では footway タグを見ない | 実データには `highway=path` に `footway=sidewalk` が付いた例がある |
| 歩道でも車線補正は掛かる | 種別係数と車線補正が独立していること |

### MIN_EDGE_FACTOR

`route.ts` の A\* が直線距離に掛けて推定値にする下限。

| ケース | 目的 |
|---|---|
| どの区間の係数もこれを下回らない | **回帰テスト。** 実際の係数より大きいと推定値が実コストを超え、最短性が壊れる。以前は route.ts に 0.8 を直書きしていたが、車線補正 0.9 で 0.72 まで下がる区間が実データに 195 本あった。種別・車線・footway の全組み合わせを走査する |
| 実際に到達しうる下限と一致する | 緩すぎる値だと探索が遅くなるだけなので、届く値であること |

**値そのものは[未決事項](./requirements.md#7-未決事項)。** 実際に歩いて調整するため、
テストは「設計表と一致すること」と「大小関係」を押さえ、値の妥当性は問わない。

## lib/db.ts — タイルの保存

`__tests__/db-test.ts`

**実際の SQLite に対してテストする。** `node:sqlite`（Node 22 に同梱）を
`expo-sqlite` と同じ形の口で包み、SQL そのものを確かめる。
実機では `lib/store.ts` が `expo-sqlite` を渡す。

保存するのは生の way / node で、グラフではない。
**グラフは読み込んだタイル全体から組み立てる**必要があるため
（あるノードが交差点かどうかは隣のタイルを読んだ時点で変わる）、
タイルごとにエッジを作って保存すると辻褄が合わなくなる。

| ケース | 目的 |
|---|---|
| 何度呼んでも落ちない | 起動のたびに `initSchema` を通すため |
| 同じスキーマなら保存済みのデータを残す | 起動のたびに消さないこと |
| 古いスキーマの DB は作り直す | **回帰テスト。** 列を変えたのに古い表が残り「no such column: w.highway」になっていた |
| バージョンが記録されていない古い DB も作り直す | **回帰テスト。** 0 を「まだ何も無い」とみなして作り直しを飛ばしていた |
| 版数が合っていても、列が足りない表は作り直す | **回帰テスト。** `PRAGMA user_version` を信用せず実際の表の形を見る |
| 使わなくなった表を残さない | `node_tiles` の取り残しを防ぐ |
| タイルから way を引くのに ways を全走査しない | **回帰テスト。** `way_tiles` の主キーは `(way_id, x, y)` で先頭が way_id のため、タイル側から引く索引が別に要る。無いと `loadTiles` が毎回 `ways` を頭から舐める（関東全域で 236 万行）。[探索 2 秒](./requirements.md#5-非機能要件)を守れない |
| 保存したタイルを取得済みと判定する | 通信するかどうかの判断 |
| 取得済みタイルを一覧できる | 何が手元にあるかの確認手段 |
| 同じタイルを二度保存しても重複しない | 再取得しても増えないこと |
| 保存した way と node をそのまま返す | タグと node 参照が往復すること |
| 使うタグだけを保存する | `highway` と `lanes` 以外は保存しない。1 タイル 784KB → 404KB の内訳の 1 つ |
| lanes が無い way でも往復する | タグ欠損 |
| 座標が丸められずにそのまま往復する | **精度を落とさないこと。** 整数化すれば縮むが採らなかった |
| ノードを多く持つ way でも往復する | 長さと順序 |
| OSM の大きな ID でも往復する | ノード ID は 100 億を超える |
| 未取得のタイルを指定しても落ちない | 初回起動 |
| タイルを指定しなければ空を返す | 空配列で SQL を組まないこと |
| 複数タイルをまとめて読める | 3×3 の読み込み |
| 境界をまたぐ way は、どちらのタイルからも読める | way は構成ノードが入るタイルすべてに入る（[タイル間の接続](./design.md#23-タイル間の接続)） |
| 両方のタイルに含まれる way を二重に返さない | OSM ID で重複排除できていること |
| 地点を保存して、タイル単位で読める | タップした場所の名前を出すため |
| 別のタイルの地点は返さない | 42 枚ぶん読むと多すぎる。近くだけ引く |
| 種別と座標がそのまま往復する | |
| タイルを指定しなければ空を返す | |
| 地点が入っていない古い DB でも落ちない | POI を持たない頃に転送した DB |
| way が参照する node は、別タイル由来でも揃う | **境界の way が欠けたノードを指さないこと。** 欠けるとその way が捨てられ、タイルが繋がらない |
| footway の種別が往復する | 歩道・横断歩道を区別できないと、コストモデルが大通り沿いの歩道を優遇してしまう（[footway の 6 割は道路の付属物](./design.md#111-footway-の-6-割は道路の付属物)） |
| footway タグが無い way でも往復する | タグ欠損。列を足しても既存の way が壊れないこと |
| 歩道が沿う幹線の種別が往復する | これが無いと幹線沿いの歩道に幹線の係数を継がせられない |
| along が無い way でも往復する | タグ欠損 |

## lib/osm-filter.ts — 抽出とタイル振り分け

`__tests__/osm-filter-test.ts`

**アプリと前処理スクリプトが共有する規則。** 別々に書くと、Step 1 の実測値と
Step 3 で生成した DB が食い違ってしまう。

| ケース | 目的 |
|---|---|
| 生活道路や歩行者専用道は通す | 歩ける道を落とさないこと |
| 歩行者が入れない道を落とす | `motorway` / `trunk` とその `_link` |
| 徒歩を禁じている道を落とす | `foot=no` |
| 私有地を落とす | `access=private` |
| 工事中や計画中を落とす | `construction` / `proposed` |
| highway が無いものを落とす | 建物や土地利用など、道ではない way |
| 知らない種別は通す | `cycleway` など。係数は 1.0 に落ちる |

## lib/route.ts — 経路探索

`__tests__/route-test.ts`

同じ 2 地点に対して、**幹線を通る直線（400m）と生活道路の迂回（577m）**の
2 通りがあるグラフで確かめる。

| ケース | 目的 |
|---|---|
| 2 地点を繋ぐ経路を返す | 出発点と目的地を含むこと |
| **幹線を避けて生活道路を選ぶ** | **このアプリの価値そのもの。** 遠回りでも生活道路を選ぶ |
| **係数を平らにすると幹線を通る** | **係数が経路を変えている証拠。** 距離だけなら短い幹線が選ばれる |
| 遠回りのぶん距離は伸びる | 幹線回避の代償が出ていること |
| 同じノードなら距離 0 の経路を返す | |
| 繋がっていなければ null を返す | 川や線路で分断された先 |
| 知らないノードを指定したら null を返す | 例外を投げないこと |
| 距離とコストの両方を返す | 係数の効き具合を見るため |
| 幹線しか道が無ければ、やむを得ず通る | **禁止ではなく高コスト。** 分断された地形で到達できなくならないこと |
| 種別ごとの距離を返す | 経路の内訳を数字で見る |
| 距離の大きい順に並べる | |

**フィクスチャの注意:** 迂回路は東へふくらませてある。まっすぐ並べると
直線と同じ長さになり、係数を平らにしたときに引き分けになってしまう。

### 履歴係数による多様性

**係数を平らにしたグラフで確かめる。** 種別で差が付かない状態にすれば、
「ルートが変わった原因は履歴だけ」と言い切れる。

| ケース | 目的 |
|---|---|
| **歩いた区間を避けて別の道を選ぶ** | **F-9 そのもの。** 短い直線を歩いたことにすると迂回へ移る |
| 履歴を渡さなければ経路は変わらない | 開発用に履歴を切って、幹線回避だけの結果と比べられること |
| 十分に時間が経った区間は避けなくなる | 2 週間経てば元のルートに戻る |
| 履歴込みのコストは種別だけのコストより高くなる | どちらがどれだけ効いたかを数字で見る |
| 全部歩いていても経路は返す | 変えられる区間が無ければ同じルートでよい。**到達不能にしない** |

### routeCoordinates

地図に線を描くための座標列。

| ケース | 目的 |
|---|---|
| 出発点から目的地へ順に並ぶ | |
| **向きが逆のエッジでも反転して繋ぐ** | エッジの geometry は way が描かれた向きで入っている。**反転を忘れると線が行ったり来たりする** |

| 途中の形状点を残す | 交差点だけを結ぶと地図上で道から外れる |
| エッジの無い経路では空を返す | 出発点と目的地が同じノードに寄った場合。線は引かない |

## 実測値との突き合わせ

前処理の抽出条件が正しいかは、`scripts/build-db.ts` が最後に出す値を
下表と突き合わせて判断する（開発タイル: 武蔵小山 `6985/1781`）。

| 項目 | 実測値 |
|---|---|
| way | 1,806 |
| node | 6,391 |
| 交差点ノード | 2,767 |
| エッジ | 3,777 |
| 総延長 | 162.9 km |
| 孤立ノード | 0 |

数値がずれた場合の切り分け:

- **way / node がずれる** → タイル計算か、`lib/osm-filter.ts` の抽出条件
- **way / node は合うがグラフがずれる** → 分割処理（`buildGraph`）
- **孤立ノードが 0 でない** → 隣接リストの構築漏れ
