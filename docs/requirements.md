# walk-app 要件定義

最終更新: 2026-08-08

## 1. 目的

**「大通りを避けた、毎回少しずつ違う散歩ルートを提案してくれる」個人用 iPhone アプリ。**

目的地までの経路は地図アプリでも出せるが、それは車向けの幹線道路を通りがちで、しかも何度検索しても同じ道を出してくる。本アプリは「歩いて気持ちのいい道」かつ「前回と違う道」を提案することを中心に据える。

作者自身が日常的に使えることを最優先とし、App Store での一般公開は目的としない。

## 3. スコープ

### やること

- 目的地を指定すると、幹線道路を避けた徒歩ルートを提案する
- 提案するたびに、前回までと一部でも違うルートを出す
- 提案ルートを地図に表示し、自分の現在地を重ねる
- 散歩の GPS 記録と履歴閲覧

### やらないこと

- App Store での配信・審査対応
- ユーザー登録／ログイン、他ユーザーとの共有
- Android 対応（コードは React Native なので将来可能だが動作確認しない）
- 音声によるターンバイターンのナビゲーション
- 周回コース（出発地に戻る）の生成 — [将来の検討事項](#8-将来の検討事項)

## 4. ルート提案エンジン

本アプリの中核。ここだけ詳細に定義する。

### 4.1 前提調査の結果

**`lanes`（車線数）タグは日本の生活道路にほぼ付いていない。**

東京の住宅地 約 1.2km 四方を Overpass API で実測した結果:

| タグ | 付与率 |
|---|---|
| `lanes` | 65/760 本 (8.6%) |
| `lanes`（`highway=residential` のみ） | **1/140 本 (0.7%)** |
| `width`（道幅） | 6/760 本 (0.8%) |
| `sidewalk`（歩道有無） | 8/760 本 (1.1%) |

したがって当初の「1 車線以下の道を優先する」は、**そのままでは実装できない**。避けたい対象である生活道路にこそデータが無い。

一方、道路種別 `highway` は全ての道に付いており、日本では道幅とよく対応する。同エリアの内訳:

```
footway 252 / service 178 / residential 140 / unclassified 51
tertiary 48 / primary 23 / steps 20 / secondary 17 / pedestrian 11 / path 11
```

**→ 道路種別を主指標とし、`lanes` が付いている場合のみ補助的に加味する方針とする。**

### 4.2 探索方式

**端末内で自前の経路探索を行う。** 外部のルーティング API は使わない。

理由:

- [要件 F-9](#f-9-ルートの多様性-p0)（過去に提案したルートのコストを上げる）は、外部 API では表現できない。自分でコスト計算を持てば 1 項足すだけで済む
- 道路種別ごとの重み付けを自由に調整できる（実際に歩いて感覚と合うまで直したい）
- 無料・オフライン動作・API キー不要

代償として実装量は増える。まずは狭いエリア・単純なコストで動くものを作り、実際に歩きながら育てる。

### 4.3 コストモデル

経路のコスト = 各区間の `距離 × 種別係数 × 履歴係数` の総和。これを最小化する経路を探索する。

**種別係数（初期値。実際に歩いて調整する）**

| OSM `highway` | 係数 | 扱い |
|---|---|---|
| `pedestrian`, `footway`, `path` | 0.8 | 歩行者専用道・公園内の道。優遇する |
| `living_street` | 0.9 | 生活道路 |
| `residential`, `unclassified` | 1.0 | **基準** |
| `service` | 1.2 | 細い路地・私道。行き止まりの可能性があるため微減点 |
| `steps` | 1.5 | 階段。距離は短いが労力がかかる |
| `tertiary` | 2.0 | ここから幹線道路 |
| `secondary` | 4.0 | |
| `primary` | 8.0 | 強く避けるが、通行は許容する |
| `motorway`, `trunk` | 通行不可 | 歩行者が入れない |

**`lanes` による補正**

タグが存在する場合のみ適用する（無い場合は補正なし）:

- `lanes >= 2` → 係数を 1.5 倍
- `lanes <= 1` → 係数を 0.9 倍

**通行不可とする道**

- `highway=motorway` / `trunk` およびその `_link`
- `foot=no`
- `access=private`

**設計上の原則: 幹線道路を完全禁止にはしない。**
川・線路・高速道路で分断された地形では、幹線道路を通らないと目的地に到達できない場合がある。高コストで「やむを得ず通る」を表現する。

### 4.4 探索アルゴリズム

- ノード = 交差点、エッジ = 交差点間の道路区間、としたグラフ上の最小コスト経路探索
- ダイクストラ法、または直線距離を推定値に使った A\* 法
- 「最短も大事にしつつ」＝ 距離をコストの基礎に置き、種別係数で歪めるという設計そのものがこれを表現している

## 5. 機能要件

### F-8: 道路網データの取得 `P0`

**エリアは固定サイズのタイル単位で取得し、必要に応じて増やしていく。**
「半径 N km を一度に取る」方式は採らない。エリアを広げるたびに全体を取り直すことになり、Overpass API への負荷も大きいため。

- 徒歩通行可能な道路を**タイル単位**で Overpass API から取得する
- 取得済みタイルは端末内に保存し、**2 回目以降はオフラインで動作する**
- 現在地や目的地が未取得のタイルにかかる場合、そのタイルを取得して既存のグラフに繋ぐ
- 取得済みタイルの一覧を確認し、個別に再取得・削除できる

#### タイルの定義

| 項目 | 値 |
|---|---|
| グリッド | 緯度・経度 **0.02度** 固定グリッド |
| タイル ID | `(floor(lat / 0.02), floor(lon / 0.02))` |
| 実サイズ | 東京付近で 約 2.2km × 1.8km ＝ **約 4.0 km²** |
| 取得サイズ | Overpass の応答 約 **1.0 MB** |
| 保存サイズ | 約 **0.19 MB** |

固定グリッドにすることで、タイル ID が座標から一意に決まり、取得済み判定と重複排除が単純になる。

#### タイル間の接続

**取得形式は way のノード参照とノード ID を含む形式（`out body; >; out skel qt;`）を使う。**
座標だけを返す形式（`out geom`）は使わない。

理由: OSM の**ノード ID でタイル間を正確に接続できる**ため。座標の浮動小数比較で同一点を判定する必要がなくなる。

実測（0.02度タイル 1 枚、武蔵小山付近）:

- way 1,806 本 / node 6,391 個
- **bbox の外にあるノード: 781 個 (12.2%)**
- **タイル境界をまたぐ way: 183 本**

Overpass は「bbox 内にノードを持つ way」を、**bbox の外まで含めた完全な形状**で返す。
したがって隣接タイルは自然に重なり合い、way ID・node ID で重複排除すればグラフが繋がる。

#### 規模の見積り

実測値 **0.047 MB/km²**（武蔵小山付近 15.9km² で way 7,448 本 / エッジ 17,361 本 / 保存 0.75MB）からの外挿:

| 範囲 | 面積 | タイル数 | 保存サイズ |
|---|---|---|---|
| 3×3 タイル（現在地の周囲） | 36 km² | 9 | 1.7 MB |
| 品川区 + 目黒区 | 37.5 km² | 約 10 | 1.8 MB |
| 半径 5km 相当 | 78.5 km² | 約 20 | 3.7 MB |
| 東京 23 区全域 | 627 km² | 約 160 | **30 MB** |

**保存容量は制約にならない。** 東京 23 区全域を持っても 30MB 程度で収まる。

実際の制約は次の 2 つ:

1. **Overpass API の利用制限** — 公共の無料サービスであり、広域の一括取得は規約違反にあたる。タイル単位で必要な分だけ、間隔を空けて取得する
2. **探索時のメモリ** — 全タイルを同時にメモリへ載せる必要はない。散歩の距離（数 km）なら探索が触るのは十数タイル程度なので、必要なタイルだけ読み込む

#### 取得のタイミング

F-8 は**開発中および小規模なエリア追加のための手段**と位置づける。
実運用では [F-10](#f-10-オフラインデータの一括投入-p1) で関東全域を事前投入するため、散歩中に F-8 が動くことは基本的に無い。

- **自動:** 現在地を含むタイルとその周囲 8 タイル（3×3、約 1.7MB）を確保する。
  ただし**モバイル通信中は自動取得を行わない**（[F-10 の方針](#f-10-オフラインデータの一括投入-p1)）
- **手動:** 未取得エリアに来た場合に、ユーザーが明示的に取得する

**取得する情報:** ノード ID と座標、way のノード参照、`highway`、`lanes`、`foot`、`access`、名称

**除外する道:** `highway=motorway` / `trunk` およびその `_link`、`foot=no`、`access=private`

**開発時の初期エリア:** 武蔵小山付近（緯度 35.620、経度 139.700）— 品川区・目黒区の境界あたり

### F-1: 地図表示と現在地 `P0`

- 地図を全画面表示し、ピンチズーム・パンができる
- 位置情報の許可を求め、現在地にマーカーを表示する
- 初期表示は現在地を中心にする
- 許可が拒否された場合の表示を用意する

**採用技術:** `react-native-maps`（iOS は Apple Maps。API キー不要）、`expo-location`

### F-4: 散歩ルートの提案 `P0`

- 目的地を指定する（地図をタップ、が最も簡単）
- 現在地から目的地までのルートを[コストモデル](#43-コストモデル)に従って探索する
- 提案ルートを地図に線で表示する
- ルートの総距離と推定所要時間を表示する
- 経路が見つからない場合の表示を用意する

**ルート形状:** 目的地あり（A→B）。周回コースは対象外。

### F-9: ルートの多様性 `P0`

**「毎回同じルートを出さない」ための要件。**

- 提案したルートの通過区間を端末内に記録する
- 過去に提案した区間はコストを上げ、選ばれにくくする（[履歴係数](#43-コストモデル)）
- 履歴係数は時間経過とともに減衰させる（例: 2 週間程度で元に戻る）
- 同じ目的地を再指定した際、**全区間ではなく一部区間が変わる**ことを許容する

**設計上の注意:** 履歴係数を強くしすぎると不自然な遠回りを提案するようになる。
「一部区間が違えばよい」という要件なので、係数は控えめに設定し、上限を設ける。

**実装順:** まず「提案した」履歴のみで動かす。[F-2](#f-2-散歩の記録-p1) 完成後、「実際に歩いた」記録も履歴に加える。

**未決:** 減衰の速さと係数の強さ。実際に何度か使って調整する。

### F-10: オフラインデータの一括投入 `P1`

**目的: 散歩中にモバイル通信を一切発生させない。**

自宅の Wi-Fi 環境で関東地方 7 県分の道路網をまとめて端末に入れ、以降は完全オフラインで動作させる。

- 事前に用意した関東地方 7 県の道路網データを、自宅 Wi-Fi 経由で端末に投入する
- 投入後は、[F-4](#f-4-散歩ルートの提案-p0) の経路探索が**通信なしで完結する**
- モバイル通信中は [F-8](#f-8-道路網データの取得-p0) の自動取得を行わない

#### 取得元: Geofabrik

**Overpass API は使わない。** 関東 7 県は 32,432 km²、タイル換算で約 8,100 枚・8 GB 相当のリクエストとなり、公共サービスの公平利用ポリシーに明確に反する。

代わりに、一括配布用に用意された Geofabrik の抽出ファイルを使う:

```
https://download.geofabrik.de/asia/japan/kanto-latest.osm.pbf   … 461 MB（実測）
```

関東地方 7 県（茨城・栃木・群馬・埼玉・千葉・東京・神奈川）が 1 ファイルにまとまっており、
配布単位がそのまま必要範囲と一致するため、県境で切り出す処理が不要になる。

#### サイズの見積り

実測した道路密度からの外挿:

| 地域の性質 | 実測地点 | 密度 |
|---|---|---|
| 密集市街地 | 武蔵小山 | 469 way/km² → 0.0535 MB/km² |
| 郊外住宅地 | 所沢 | 403 way/km² → 0.0526 MB/km² |
| 山間部 | 秩父 | 6 way/km² → 0.0050 MB/km² |

市街地と郊外はほぼ同density、山間部は約 1/10。関東 7 県 32,432 km² を土地利用の比率で加重すると、
**保存サイズは約 800〜900 MB** と見積もられる。iPhone の容量として問題ない。

#### 前処理

**Mac 側で前処理を行い、完成した DB を端末に転送する。**
端末上で PBF を解析したり数百万行を挿入したりはしない（時間がかかりすぎる）。

1. Mac で `kanto-latest.osm.pbf` を取得
2. Mac で歩行道路のみを抽出し、[タイル](#タイルの定義)に分割して SQLite DB を生成
3. Mac でローカル HTTP サーバを立て、アプリが自宅 Wi-Fi 経由で DB を取得する

**前処理の実装言語は Node.js。**
このプロジェクト自体が Node であり、純 JS の PBF パーサが使えるため。
Python は使えない（この Mac は Python 3.7 で pyosmium がビルドできず、Homebrew も macOS 12 で壊れている → [環境制約](#7-環境制約)）。

前処理スクリプトは `scripts/` に置き、アプリ本体とは分離する。

#### 設計上の前提

[F-8](#f-8-道路網データの取得-p0) のタイル方式をそのまま流用する。
一括投入は「同じテーブルにまとめて書き込む」だけであり、**アプリ側の経路探索・タイル管理は一切変更しない。**

**未決:** 転送方式（完成した SQLite ファイルを丸ごと 1 回で転送するか、タイル単位に分けて転送するか）。
前者が単純で速いが、中断時にやり直しになる。実装時に決める。

### F-7: ルートの追従 `P1`

- 散歩中、提案ルートの線と自分の現在地マーカーが地図上に同時に表示され続ける
- 地図が現在地に追従する（追従の ON/OFF ができる）

**必要なレベル:** 地図表示のみ。曲がり角での通知・音声案内は行わない。

### F-2: 散歩の記録 `P1`

- 「開始」「停止」で記録を制御する
- 記録中の軌跡を地図に線で描画する
- 終了時に総距離・所要時間・平均ペースを集計する

**採用技術:** `expo-location` の `watchPositionAsync()`

**制約:** フォアグラウンド記録のみ。画面を消すと止まる（→ [F-6](#f-6-バックグラウンド記録-p3)）。

**注意:** GPS は静止中も座標が揺れるため、素直に足すと距離が過大になる。実際に歩いて誤差を見てから対処する。

### F-3: 散歩履歴の閲覧 `P2`

- 記録した散歩を一覧表示する（日時・距離・所要時間）
- 選択するとルートを地図に表示する
- 削除できる

### F-5: 周辺スポット表示 `P3`

- 公園・カフェ・神社などを地図に表示する

[F-8](#f-8-道路網データの取得-p0) で Overpass を扱えるようになるため、同じ仕組みで実現できる。

### F-6: バックグラウンド記録 `P3`

- 画面を消していても記録が継続する

**前提条件:** 開発ビルド必須（Expo Go 不可）。[環境制約](#7-環境制約)により現状は着手できない。

## 6. 非機能要件

| 項目 | 決定 |
|---|---|
| 対象プラットフォーム | iOS（iPhone 実機） |
| データ保存先 | 端末内のみ。サーバー・クラウド同期はしない |
| オフライン動作 | **散歩中は完全オフラインで動作すること。** 外出中にモバイル通信を発生させない |
| 配布方法 | 開発中は Expo Go。App Store 配信はしない |
| 位置情報の扱い | 端末外に送信しない |
| 外部通信 | 自宅 Wi-Fi 環境での道路網データ投入時のみ（[F-10](#f-10-オフラインデータの一括投入-p1)）。散歩中は通信しない |

### 保存方式

保存するデータは 3 種類:

1. 道路網グラフ（[F-8](#f-8-道路網データの取得-p0)）— タイル単位。1 タイルあたり way 約 1,800 本
2. ルート提案履歴（[F-9](#f-9-ルートの多様性-p0)）— 区間 ID の集合と日時
3. 散歩の記録（[F-2](#f-2-散歩の記録-p1)）— 座標の時系列

**`expo-sqlite` を採用する。**

理由: 道路網がタイル単位で増えていく設計になったため、「必要なタイルだけ読み込む」「タイル単位で削除する」という部分的な読み書きが必須になった。`AsyncStorage` は Key-Value 全体の読み書きになるため、この用途に合わない。

タイルを Key とした Key-Value でも成立はするが、[F-9](#f-9-ルートの多様性-p0) の「過去に提案した区間」を区間 ID で引く操作もあるため、最初から SQLite にしておく。

## 7. 環境制約

**重要: 開発マシンではネイティブビルドができない。**

| 項目 | 現状 | Expo SDK 54 の要求 |
|---|---|---|
| macOS | 12.7.6 (Monterey) | Xcode 16.1 のために 14 以上が必要 |
| Xcode | 未インストール（Command Line Tools のみ） | 16.1 以上 |

### 前処理環境で使えるもの・使えないもの

[F-10](#f-10-オフラインデータの一括投入-p1) の前処理を Mac 上で行うにあたっての制約:

| ツール | 可否 |
|---|---|
| **Node.js v22.23.2** | **使える。前処理はこれで実装する** |
| Python | 使えない（3.7 系のため pyosmium がビルド不可） |
| Homebrew | 使えない（macOS 12 で formula がエラー。`osmium` 等が入らない） |
| gh CLI | 公式ビルド済みバイナリを `~/.local/bin/gh` に配置済み |

### 影響

- `npx expo run:ios` によるローカルビルドは**不可**
- 開発ビルドが必要な [F-6](#f-6-バックグラウンド記録-p3) は**着手不可**
- 一方、Expo Go はビルド不要で App Store から入手できる。
  **F-8・F-1・F-4・F-9・F-7・F-2・F-3・F-5 は Expo Go で開発・動作確認できる**

### 解消するには（将来必要になったら）

1. macOS を 14 以上にアップグレードし Xcode 16.1 以上を入れる
2. EAS Build（クラウドビルド）を使う。ただし実機用の開発ビルドには Apple Developer Program（年 $99）が必要
