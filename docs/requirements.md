# walk-app 要件定義

最終更新: 2026-08-08

実現方法・調査データ・技術選定の根拠は [design.md](./design.md) を参照。
このドキュメントは「何を満たすべきか」だけを扱う。

## 1. 目的

**「大通りを避けた、毎回違う散歩ルートを提案してくれる」個人用 iPhone アプリ。**

目的地までの経路は地図アプリでも出せるが、車向けの幹線道路を通りがちで、何度検索しても同じ道を出してくる。本アプリは「歩いて気持ちのいい道」かつ「前回と違う道」を提案することを中心に据える。

作者自身が日常的に使えることを最優先とし、App Store での一般公開は目的としない。

## 3. スコープ

### やること

- 目的地を指定すると、幹線道路を避けた徒歩ルートを提案する
- 提案するたびに、まだ歩いていない道を優先して、前回までと違うルートを出す
- 提案ルートを地図に表示し、自分の現在地を重ねる
- 散歩中、経路探索のために通信しない

### やらないこと

- **関東地方の外での利用。** 圏外で道路データを取りに行く逃げ道は設けない
- **散歩の軌跡の保存と、履歴画面での閲覧**
- App Store での配信・審査対応
- ユーザー登録／ログイン、他ユーザーとの共有
- Android 対応（コードは React Native なので将来可能だが動作確認しない）
- 音声によるターンバイターンのナビゲーション
- 周回コース（出発地に戻る）の生成 — [将来の検討事項](#6-将来の検討事項)

## 4. 機能要件

### 用語: 1 回の散歩

**目的地を指定してルートが提案された時点で始まり、ユーザーが破棄するか、次の目的地を指定した時点で終わる。**

到着したかどうかは判定しない。
[F-7](#f-7-ルートの追従) の追従と [F-11](#f-11-歩いた道の記録) の記録は、この間だけ動く。

### F-1: 地図表示と現在地

- 地図を全画面表示し、ピンチズーム・パンができる
- 位置情報の許可を求め、現在地にマーカーを表示する
- 初期表示は現在地を中心にする
- 許可が拒否された場合の表示を用意する

**地図の出所:** Apple Maps。道路・建物・公園・水域・鉄道・POI・地名が表示される。
[F-10](#f-10-オフラインデータの一括投入) で投入する道路網は経路探索専用で、画面には出ない。

**タイルはオンラインで取得される。** 未表示のエリアへ動かすと通信が発生するが、
これは[オフライン要件の対象外](#5-非機能要件)とする。

### F-4: 散歩ルートの提案

- **地図をタップして目的地を指定する**
- 現在地から目的地までのルートを探索する
- **幹線道路を避けること**
- 提案ルートを地図に線で表示する
- ルートの総距離と推定所要時間を表示する（歩き切れるかの判断材料）
- 探索中であることが分かること（遠い目的地では時間がかかるため）
- 経路が見つからない場合の表示を用意する

**ルート形状:** 目的地あり（A→B）。周回コースは対象外。

**最短性の扱い:** コストの基礎が距離なので、遠回りは自然に不利になる。
**距離の上限は設けない。** 幹線道路の回避と多様性をどこまで優先するかは、
[種別係数と履歴係数](./design.md#13-コストモデル)の調整で決める。

→ [コストモデルと探索方式](./design.md#1-ルート提案エンジン)

### F-7: ルートの追従

- [散歩中](#用語-1-回の散歩)、提案ルートの線と現在地マーカーが地図上に同時に表示され続ける
- 地図が現在地に追従する（追従の ON/OFF ができる）
- **現在地からルートを引き直せること。** 引き直しはユーザーの操作によるものとし、
  ルートを外れても自動では再探索しない

### F-11: 歩いた道の記録

**[F-9](#f-9-ルートの多様性) が使う履歴の実体。**

- [散歩中](#用語-1-回の散歩)、現在地を道路網の区間に対応付け、通過した区間を記録する
- **連続する複数の位置点が同じ区間に対応したときだけ「歩いた」とみなす**
- 記録するのは**区間 ID と日時のみ**。座標の軌跡は保存しない

**なぜ複数点を要求するか:** 日本の住宅地では平行する細い道の間隔が GPS 誤差と同程度で、
1 点だけなら隣の道に対応してしまう。誤って記録された区間は
[履歴係数](./design.md#13-コストモデル)で強く避けられ、**一度も歩いていない道が提案されなくなる。**
単発の誤対応を落とすことで、これを防ぐ。

### F-9: ルートの多様性

**「毎回同じルートを出さない」ための要件。**

- **過去に歩いた区間（[F-11](#f-11-歩いた道の記録)）は選ばれにくくする**
- **未踏の道を優先する**
- その効果は時間経過とともに減衰させる
- 変えられる区間が無ければ、同じルートを提案してよい

**重みの方針:** 最短性よりも、[道路種別](./design.md#13-コストモデル)と多様性を優先する。
ただし幹線道路の回避（`primary` 8.0）ほどではなく、多様性の重みはその下に置く。

**提案しただけのルートは対象外。** 行き先を決めかねて何度かタップしても履歴は汚れない。

→ [履歴係数](./design.md#13-コストモデル)

### F-10: オフラインデータの一括投入

- 関東地方 7 県分の道路網を、Wi-Fi 接続時にまとめて端末に投入する
- **投入前に空き容量を確認し、足りなければ開始しない**（転送の途中で失敗させない）
- 投入後は [F-4](#f-4-散歩ルートの提案) の経路探索が**通信なしで完結する**
- **端末上での事前処理は 5 分以内**（転送そのものの時間は除く）
- 同じ手順でデータを更新できる。**更新しても [F-11](#f-11-歩いた道の記録) の記録が失われないこと**
- **道路網が未投入の状態で起動したら、投入を促す案内を出す**

**更新頻度:** 年 1 回程度（[根拠](./design.md#34-更新の頻度)）。

→ [取得元と前処理](./design.md#3-オフラインデータの一括投入)

## 5. 非機能要件

| 項目 | 決定 |
|---|---|
| 対象プラットフォーム | iOS 15.1 以上（iPhone 実機）。Expo SDK 54 の下限に従う |
| データ保存先 | 端末内のみ。サーバー・クラウド同期はしない |
| オフライン動作 | **経路探索は通信なしで完結すること。** 地図タイル（Apple Maps）の通信は対象外 |
| 外部通信 | **道路網を投入するときだけ。** それも Wi-Fi 接続時に限る |
| 探索の応答時間 | **直線距離 10km 以内の目的地で、タップからルート表示まで 2 秒以内。** それより遠い場合は制限しない |
| バッテリー | **4 時間の散歩でバッテリー消費 40% 以内。** 位置取得の間隔はこれを基準に決める |
| 位置情報の扱い | 端末外に送信しない |
| 配布方法 | 開発中は Expo Go。App Store 配信はしない |

### 環境制約

**開発マシンではネイティブビルドができない**（macOS 12 に Xcode 16.1 が入らないため）。

現時点の全機能は Expo Go で動く想定。
**[F-10](#f-10-オフラインデータの一括投入) の DB は実際に生成して 670MB だった**ので、
Expo Go で検証済みの 900MB の内側に収まる（[実測](./design.md#実際に作った結果2026-08-08-実測)）。
残るのは、その DB を端末に置いて `expo-sqlite` から読めることの確認だけ。

読めなければネイティブビルドが必要になり、
macOS のアップグレードか Apple Developer Program（年 $99）の費用が発生する。

→ [詳細と解消手段](./design.md#5-開発環境)

## 6. 将来の検討事項

- **周回コース**（出発地に戻るコース）の生成。「30 分歩いて帰ってくる」型。
  A→B とはアルゴリズムが別物になるため、F-4 完成後に改めて検討する
- **夜道の明るさ**を考慮する（OSM の `lit` タグ。付与率は未調査）
- **坂道**の回避／選好（標高データが別途必要）

## 7. 未決事項

- [ ] Expo Go が実際の DB（670MB）を扱えるか — ダミー 900MB は検証済み。実物での確認が残っている
- [ ] **`footway` の 0.8 が、大通りの歩道を選ばせていないか** — 10km の経路で 88% が
      `footway` になった。日本では大通りの歩道が `footway` で別に描かれているため、
      「幹線を避ける」つもりが「幹線の歩道を歩く」になっている疑いがある。
      DB は `footway=sidewalk` の区別を保存していないので、確かめるには前処理から見直す必要がある
- [ ] 種別係数（`footway` 0.8 〜 `primary` 8.0）が妥当か — 実際に歩いて調整
- [ ] 履歴係数 3.0 が妥当か、減衰速度をどうするか — 実際に歩いて調整
- [ ] マップマッチングの許容距離と、「歩いた」とみなす連続点数 — 実際に歩いて調整
- [ ] F-10 の転送方式 — DB 丸ごとかタイル単位か

### 解決済み

- ~~保存方式~~ → `expo-sqlite`
- ~~道路網を取得する範囲~~ → 0.02度の固定グリッドによるタイル方式
- ~~ルーティング API の選定~~ → 外部 API を使わず端末内で自前探索
- ~~目的地の指定方法~~ → 地図タップ。オフラインで地名検索はしない
- ~~多様性の判断材料~~ → 提案したルートではなく、実際に歩いた区間
