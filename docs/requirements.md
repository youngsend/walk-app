# walk-app 要件定義

最終更新: 2026-08-08

実現方法・調査データ・技術選定の根拠は [design.md](./design.md) を参照。
このドキュメントは「何を満たすべきか」だけを扱う。

## 1. 目的

**「大通りを避けた、毎回少しずつ違う散歩ルートを提案してくれる」個人用 iPhone アプリ。**

目的地までの経路は地図アプリでも出せるが、車向けの幹線道路を通りがちで、何度検索しても同じ道を出してくる。本アプリは「歩いて気持ちのいい道」かつ「前回と違う道」を提案することを中心に据える。

作者自身が日常的に使えることを最優先とし、App Store での一般公開は目的としない。

## 3. スコープ

### やること

- 目的地を指定すると、幹線道路を避けた徒歩ルートを提案する
- 提案するたびに、前回までと一部でも違うルートを出す
- 提案ルートを地図に表示し、自分の現在地を重ねる
- 散歩中、経路探索のために通信しない

### やらないこと

- **散歩の GPS 記録と履歴の閲覧**
- App Store での配信・審査対応
- ユーザー登録／ログイン、他ユーザーとの共有
- Android 対応（コードは React Native なので将来可能だが動作確認しない）
- 音声によるターンバイターンのナビゲーション
- 周回コース（出発地に戻る）の生成 — [将来の検討事項](#6-将来の検討事項)

## 4. 機能要件

### 用語: 1 回の散歩

**目的地を指定してルートが提案された時点で始まり、ユーザーが破棄するか、次の目的地を指定した時点で終わる。**

到着したかどうかは判定しない。

[F-9](#f-9-ルートの多様性-p0) の履歴はこの単位で扱う。

### F-8: 道路網データの取得 `P0`

- 徒歩通行可能な道路を**タイル単位**で取得する
- 取得済みタイルは端末内に保存し、2 回目以降はオフラインで動作する
- 未取得のタイルにかかる場合、そのタイルを取得して既存のグラフに繋ぐ
- **モバイル通信中は自動取得を行わない**

開発中と小規模なエリア追加のための手段。実運用のデータ投入は [F-10](#f-10-オフラインデータの一括投入-p0) が担う。

→ [タイル方式の設計](./design.md#2-道路網データ)

### F-1: 地図表示と現在地 `P0`

- 地図を全画面表示し、ピンチズーム・パンができる
- 位置情報の許可を求め、現在地にマーカーを表示する
- 初期表示は現在地を中心にする
- 許可が拒否された場合の表示を用意する

**地図の出所:** Apple Maps。道路・建物・公園・水域・鉄道・POI・地名が表示される。
[F-8](#f-8-道路網データの取得-p0) で取得する道路網は経路探索専用で、画面には出ない。

**タイルはオンラインで取得される。** 未表示のエリアへ動かすと通信が発生するが、
これは[オフライン要件の対象外](#5-非機能要件)とする。

### F-4: 散歩ルートの提案 `P0`

- **地図をタップして目的地を指定する**
- 現在地から目的地までのルートを探索する
- **幹線道路を避けつつ、最短性も損なわないこと**
- 提案ルートを地図に線で表示する
- ルートの総距離と推定所要時間を表示する（歩き切れるかの判断材料）
- 経路が見つからない場合の表示を用意する

**ルート形状:** 目的地あり（A→B）。周回コースは対象外。

→ [コストモデルと探索方式](./design.md#1-ルート提案エンジン)

### F-9: ルートの多様性 `P0`

**「毎回同じルートを出さない」ための要件。**

- **[1 回の散歩](#用語-1-回の散歩)につき、最終的に提案されたルート 1 本の通過区間を記録する。**
  途中で引き直した分は履歴に残さない
- 過去に提案した区間は選ばれにくくする
- その効果は時間経過とともに減衰させる
- 同じ目的地を再指定した際、**全区間ではなく一部区間が変わる**ことを許容する
- 多様性のために不自然な遠回りを提案しないこと
- 変えられる区間が無ければ、同じルートを提案してよい
- **[同じ散歩](#用語-1-回の散歩)の途中での再探索では、直前に提案したルートを避けないこと**

→ [履歴係数](./design.md#13-コストモデル)

### F-10: オフラインデータの一括投入 `P0`

- 関東地方 7 県分の道路網を、Wi-Fi 接続時にまとめて端末に投入する
- 投入後は [F-4](#f-4-散歩ルートの提案-p0) の経路探索が**通信なしで完結する**
- **端末上での事前処理は 5 分以内**（転送そのものの時間は除く）
- 同じ手順でデータを更新できる。**更新しても [F-9](#f-9-ルートの多様性-p0) の提案履歴が失われないこと**

**更新頻度:** 年 1 回程度（[根拠](./design.md#34-更新の頻度)）。

→ [取得元と前処理](./design.md#3-オフラインデータの一括投入)

### F-7: ルートの追従 `P1`

- 散歩中、提案ルートの線と現在地マーカーが地図上に同時に表示され続ける
- 地図が現在地に追従する（追従の ON/OFF ができる）
- **現在地からルートを引き直せること。** 引き直しはユーザーの操作によるものとし、
  ルートを外れても自動では再探索しない

## 5. 非機能要件

| 項目 | 決定 |
|---|---|
| 対象プラットフォーム | iOS（iPhone 実機） |
| データ保存先 | 端末内のみ。サーバー・クラウド同期はしない |
| オフライン動作 | **経路探索は通信なしで完結すること。** 地図タイル（Apple Maps）の通信は対象外 |
| 外部通信 | **自動の通信は Wi-Fi 接続時のみ。** モバイル通信を使うのは、ユーザーが明示的に指示したときに限る |
| バッテリー | **4 時間の散歩でバッテリー消費 40% 以内**（[F-7](#f-7-ルートの追従-p1) にかかる要件。位置取得の間隔はこれを基準に決める） |
| 位置情報の扱い | 端末外に送信しない |
| 配布方法 | 開発中は Expo Go。App Store 配信はしない |

### 環境制約

**開発マシンではネイティブビルドができない**（macOS 12 に Xcode 16.1 が入らないため）。

現時点の全機能は Expo Go で開発・動作確認できるため、支障はない。

→ [詳細と解消手段](./design.md#5-開発環境)

## 6. 将来の検討事項

- **周回コース**（出発地に戻るコース）の生成。「30 分歩いて帰ってくる」型。
  A→B とはアルゴリズムが別物になるため、F-4 完成後に改めて検討する
